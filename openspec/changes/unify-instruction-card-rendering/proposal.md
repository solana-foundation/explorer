# Proposal: Unify instruction card rendering across the tx page and inspector

## Context

- About 78 `*DetailsCard` components render instructions on two surfaces: `/tx/[signature]` and the inspector. 71 of them draw a card frame.
- Surface chrome leaks into the cards as props. `InstructionCardComponent` swaps the frame in 7 files. `AssociatedTokenDetailsCard` also takes `AddressComponent` and `showProgramField`. `innerCards: JSX.Element[]` is built eagerly in `InstructionsSection` and threaded through four layers to reach `BaseInstructionCard`, so every card in between declares a prop it never reads. The inspector invents `INSPECTOR_RESULT` and `INSPECTOR_SIGNATURE` purely to satisfy card signatures.
- Row markup is copied per field. The 13 System cards were 815 lines, almost all of it `<BaseTable.Row><Cell>label</Cell><Cell className="text-right">…</Cell></BaseTable.Row>` repeated.
- `unify-instruction-parsing` named this work as an explicit out-of-scope follow-up: "collapsing the two per-surface card switches into one render pipeline."
- That change is also what makes the leak observable for System. The inspector reaches System cards only because it landed the System slice and the shared dispatcher — `inspector/InstructionsSection.tsx` calls `dispatcher.fromTransactionInstruction(ix)` and routes its `SYSTEM_PROGRAM_LABEL` case to `SystemDetailsCard`. Before it, the inspector's own `into-parsed-data.ts` fed a separate path. System is therefore a program where one card component must already satisfy two surfaces, while still hardcoding the tx-page frame for both.

## Why

A card should describe what an instruction means. It should not know which page it is on. Today those two responsibilities share one prop bag, so every new surface concern becomes a new prop on every card, and every field becomes eight lines of table markup.

Making chrome ambient (React Context) and fields declarative (data) separates them. Cards shrink to their actual content, and the surfaces stop needing to agree by convention.

### Alternatives considered

- **One `InstructionCard` with a `mode` flag.** Rejected — merges both surfaces' chrome into a conditional. Same coupling, different shape.
- **Keep component injection, just formalise the prop names.** Rejected — the prop count grows with every surface concern, and it is already three (`InstructionCardComponent`, `AddressComponent`, `showProgramField`) for one card.
- **Migrate all 71 cards in one pull request.** Rejected as unreviewable. 15 are inspector-reachable and carry real chrome deltas that need eyes; the other 56 are mechanical.
- **Start with a tx-page-only program (Stake or Vote, 14 cards each).** Rejected. Zero behaviour risk, but it never exercises the second surface, so the design would land unproven on the only axis that motivates it. System is the one program that is large, inspector-reachable, *and* hardcodes its frame. Its existing test coverage is uneven, and only the inspector side pins the migration: `InspectorPage-SystemProgram.spec.tsx` asserts label-and-value for every row of 9 of the 13 instructions, while `SystemDetailsCard.spec.tsx` covers the tx page with 2 of 13 (Transfer, TransferWithSeed) and asserts only the card title. The tx-page rows are therefore pinned by DOM diffing against a `HEAD` worktree rather than by assertions — see **Impact** below. Closing that gap is a follow-up.
- **Make the field DSL mandatory.** Rejected, and the audit says how often it would bite: ~12 of the 71 frame-drawing cards derive content from a hook, so a pure `fields(info)` cannot produce it. Those cards write their own component and still use `InstructionFields` for the rows they can express. Making the DSL mandatory would have forced hook results through props, pushing the fetching back up into the dispatcher — the coupling this change exists to remove.
- **Build the instruction node tree in the first pull request.** Deferred to the last one. The tree is independent of the surface split and would have roughly doubled the first diff.
- **Keep the tier order of each surface in the router.** Rejected. The inspector tried a fetched IDL before the curated card, so it replaced a curated card with the IDL card about a second after load ([HOO-1194](https://linear.app/solana-fndn/issue/HOO-1194/inspector-prefers-a-fetched-idl-over-curated-instruction-cards)). One order on both surfaces also leaves one tier sequence.
- **Key the router by program id.** Rejected. Token and Token-2022 share one card, and Pyth, Serum and Memo each have several program ids. The dispatcher maps a program id to one program label, so the router keys by that label.
- **Give child cards a React Context of their own.** Rejected. Fewer tests construct a surface, but a second provider beside `InstructionSurface` gives two sources for how a card renders.
- **Keep `SignatureContext` and read it in the Anchor event hook.** Rejected. The diff is smaller, but `SignatureContext` defaults to `''`, so an empty string means a missing signature. `InstructionSurface` types a missing signature as `undefined` and requires the key on every surface. The cost is that every frame render needs a surface. 8 tests in 1 spec and 4 story files rendered a frame without one.
- **Keep a per-surface address renderer.** Rejected. The inspector used `AddressWithContext` with `hideInfo`, which renders the same `<Address link alignRight>` as the tx page. A second renderer adds a field to `InstructionSurface` and changes nothing on screen.
- **Put both surfaces in the entity.** Rejected for the inspector at first, because `InspectorInstructionCard` imported this entity's barrel. The router replaced that card and takes `Card` from the page, so both surfaces live in the entity, which also lets card tests pick a surface without reaching across layers.

## What Changes

- Add to `app/entities/instruction-card/`:
  - `model/surface.tsx` — `InstructionSurface` (card router, `result`, `signature`, `instructionData`, `rawInstructions`, `collapsible`, `validateProgram`) delivered by Context. `useInstructionSurface` throws outside a provider, matching `useInstructionParser`. The cards read the signature from `InstructionSurface`. A missing signature throws no error. A card then shows no program events. `signature` is therefore a required key. The card body draws the `Program` row in the decoded view on both surfaces, so the frame needs neither the width of the body nor the program name. A frame draws its own `Program` row only in the raw view.
  - `model/node.ts` — `InstructionNode`, one object replacing the `ix` + `index` + `childIndex` + `raw` + `innerCards` spread. It states `programId` as its own field.
  - `model/fields.ts` — field kinds such as `address`, `sol`, `bytes`, `string` and `text`. `text` takes `string | number`, and no kind takes markup, so the descriptors stay data.
  - `ui/InstructionFields.tsx` — renders the label and value rows of migrated cards. The leading `Program` row is the exception: `ProgramField` owns that markup, because the inspector puts its own validator on that row.
  - `ui/ValueCell.tsx` — formats a value by its kind. Field rows and argument rows both render `ValueCell`, to give each kind one format.
  - `ui/DecodedInstructionCard.tsx`, with `model/args.ts` and `model/accounts.ts` — the card of an instruction that a Codama client decodes (Codama IDL, Lighthouse, SAS, PMP). `DecodedInstructionCard` renders the instruction's accounts with role badges. The argument table has a Type column and expandable nested arguments.
  - `ui/InstructionCardView.tsx` — draws the frame with the flags of the surface. The escape hatch for cards that need their own markup, and the carrier for card-derived program events via an `events` prop.
  - `model/define-instruction-card.tsx` — shorthand factory for the common label/value shape.
  - `ui/TxInstructionSurface.tsx` — the transaction page surface.
  - `ui/BaseInstructionCard.tsx` — the frame of both surfaces, moved from `app/components/common/`.
  - `ui/InstructionNodeCards.tsx` — renders a list of nodes through `InstructionSurface.Card`, and a card with a note for a node the page cannot resolve.
- The entity declares `inspectorSurface` in `ui/inspector-surface.tsx`. `inspectorSurface` builds the surface of one message. Specs import that module, so a spec renders the real inspector surface. The surface sets `signature` to `undefined`, because the inspector reads its logs from a simulation, not from a fetched transaction. `INSPECTOR_RESULT` and `INSPECTOR_SIGNATURE` are deleted, because no card takes `result` or `signature` as a prop.
- Migrate all 13 System cards to `defineInstructionCard`. No file under `app/components/instruction/system/` imports `Address`, `BaseTable`, or `InstructionCard` any more.
- Migrate every other program to the surface, one program per pull request: Stake, Vote, Address Lookup Table, Pyth, the single-card programs, the decoded instruction tables, the unknown card, Associated Token, Compute Budget, ZK ElGamal Proof, Token Metadata, Anchor, Token and Token-2022 with the batch cards, and BPF Upgradeable Loader.
- Replace the two per-surface routing switches with one router, `InstructionNodeCard` in `app/components/instruction/`. The router dispatches an instruction and picks the card by the program label of the dispatch result. Both surfaces put the router on `InstructionSurface` as `Card`, because the entity cannot import the card of every program.
- Build the node tree before render. The tx page builds it with `toInstructionNodes`, and the inspector builds it in its `InstructionsSection`. `InstructionCardView` renders `InstructionNode.children` through `InstructionSurface.Card`. `innerCards` is deleted.
- Add `instructionData` to `InstructionSurface`. An ed25519 instruction can point into the data of another instruction, so the router passes the lookup to `Ed25519DetailsCard`. The lookup replaces `siblingDataFromParsedTransaction` and the inspector's own lookup.
- Delete `SignatureContext`. The cards read the signature from `InstructionSurface`, so no other React Context carries the signature. The receipt page provided `SignatureContext` and rendered no instruction card.

**Out of scope**: reshaping `InstructionNode.ix`, which waits for `unify-instruction-parsing` to drop the compat wrap.

## Impact

- **Transaction page: no change to the System cards.** Verified empirically for the two fixtures that exist — the rendered cell text, button set, wrapper elements, and `<code>` counts are identical to `HEAD` for Transfer and TransferWithSeed. Every piece is the same component with the same props, which is the argument that carries the other 11 instructions; they have no tx-page fixture to diff.
- **Inspector: three chrome deltas on System cards**, because they previously used the *tx-page* frame on both surfaces. A collapse chevron now appears (the inspector surface sets `collapsible`); Raw mode gains the hex and accounts block, because `raw` is now forwarded; the Raw-mode Program row uses `AddressWithContext` with `programValidator`. Row labels, order, count, and the single Program row are unchanged. Address rows render the same `Address` as the tx page. All three deltas match the inspector chrome of Token, Token-2022, and ATA.
- **The inspector keeps the curated card when an IDL resolves.** The inspector used to check the dynamic IDL tier *before* its program switch, so once an IDL resolved for the System program, the IDL card replaced `SystemDetailsCard`. Measured against the dev server with the `CreateAccount` fixture, `SystemDetailsCard` was on screen for roughly 0.75–1.75 s before the IDL card replaced it. The tx page had the opposite order. `InstructionNodeCard` uses the tx-page order on both surfaces, which settles [HOO-1194](https://linear.app/solana-fndn/issue/HOO-1194/inspector-prefers-a-fetched-idl-over-curated-instruction-cards). The unit tests mock the IDL hook, so they pin this order without a network.
- **Behaviour changes of the router.** The inspector renders a raw `GetMinimumDelegation` instruction with `RawStakeDetailsCard`, where the IDL card or the unknown card showed it before. `RawStakeDetailsCard` hands every other stake instruction to the IDL card when an IDL decodes it, on both surfaces. On the tx page, such an instruction showed the unknown card before. The tx page renders a raw System, Token, Associated Token, Memo, Address Lookup Table or BPF instruction with its curated card when the parser slice decodes it; before, such an instruction reached the IDL card or the unknown card. The router renders every card inside an ErrorBoundary, so a top-level card that throws shows the unknown card on both surfaces, or the IDL card for a PMP instruction that an IDL decodes. An instruction or CPI that the page cannot resolve shows an `Unknown Instruction` card with the note `Could not display instruction #i.j, please report`.
- **Behaviour changes of the Token and BPF Upgradeable Loader cards.** A field whose value is `null` shows `(none)`, as the token batch card does. The Token card drew a blank cell there, and the BPF Upgradeable Loader card drew a grey `None`. A Token boolean shows `true` or `false`, where the cell was blank, and a Token list of extension types shows one entry per line, where the entries ran together. The BPF Upgradeable Loader `write` bytes wrap at 50 characters, as the BPF Loader `write` card does. The Token card shows a `Program` row in the decoded view on the tx page, as the BPF Upgradeable Loader card already did, and the token batch card shows one on both surfaces. In the inspector, the token batch card moves from the tx-page frame to the inspector frame.
- **`InstructionNode.ix` is provisional.** It is typed `ParsedInstruction | TransactionInstruction` because the *frame* — not the card — branches on `'parsed' in ix` to choose `BaseRawParsedDetails` over `BaseRawDetails` for the Raw view. When `unify-instruction-parsing`'s follow-up stops producing `ParsedInstruction`, this field has to split into roughly `programId` + `raw` + an optional RPC-parsed payload. `programId` is already split out, for exactly this reason: a card needs it to feed `InstructionFields`, and taking it from `node.ix` at ~12 future call sites would have put those cards in the blast radius of the reshape. As it stands the revision touches the frame, the router, `instructionDataOf` and the two node builders; no program card is affected, because no program card reads `node.ix`.
- **Interaction with `unify-instruction-parsing`: this change shrinks its remaining work.** The System slice's canonical `SystemParsed` is built from the same superstruct types the cards take — `system-parser.ts` imports `TransferInfo`, `CreateAccountInfo`, and the rest from `@components/instruction/system/types`, and those resolve to web3.js `PublicKey` via `PublicKeyFromString`. So `defineInstructionCard<TransferInfo>` already consumes the slice's shape, and the `address(label, pubkey: PublicKey)` descriptor is correct after the compat wrap is deleted. Migrating System off the wrap therefore touches **one** file — `SystemDetailsCard` drops its two `create(...)` passes and switches on `sliceParsed.type` instead — rather than re-editing 815 lines of card JSX. Note this alignment exists because `system-parser.ts` imports a web3.js type, which the parser proposal's own rule forbids for slice internals; that pre-existing tension is what makes the two shapes identical today.
- **The field DSL's reach is narrower than System suggests — there are two card styles, not one.** `defineInstructionCard` calls `title` and `fields` as plain functions, so a card whose content depends on a hook cannot use it. An audit of all 71 frame-drawing cards found ~12 in that position: most call `useCluster` for a `url`, and `TokenDetailsCard` resolves mint decimals through `useMintAccountInfo` + `useSWR` to format an amount. Those cards write their own component — which *can* call hooks — and keep `InstructionFields` for the rows they can express. Both styles take chrome from the surface, so the coupling this change removes is removed for all 71; only the factory's brevity is unavailable to the 12. The headline 815 → 155 ratio comes from System, the most uniform program in the repo, and will not generalise at that rate.
- **Program events are a card-derived view prop, not node data.** Unlike CPIs, which the page builds into the node tree, events are read from transaction logs *inside* the card (`useAnchorEvents`), and exist only on the tx page — the inspector has no logs, so its cards have no events. They therefore arrive as `InstructionCardView`'s `events` prop rather than on `InstructionNode`, and the factory cannot produce them. One card uses them, `AnchorDetailsCard`.
- **Audit of the capabilities this design must carry.** Beyond events, the same sweep found: `defaultRaw` used by one card (Serum), which a card with no children replaces; `headerButtons` used by **no** card, so the frame drops it; `collapsible` used by the token batch card; and **no card renders sibling cards**, every one renders exactly one frame.
- **Line count.** System leaf cards 815 → 155. The two routing switches 1065 → 348, counting `InstructionNodeCard` and `toInstructionNodes`. The last four steps (Token, BPF Upgradeable Loader, the router with the node tree, and the frame move) add 654 and delete 1614 lines of application code, without tests and stories.
- **Verification.** `tsc --noEmit` clean; eslint clean including `boundaries/dependencies`; the full spec suite passes (378 files, 4122 tests, after the rebase onto `a2107a74`); `next build` compiles with no measurable bundle change — a fresh `build:info` on this branch is byte-identical to one on `master`. Parity was probed by rendering both surfaces against a `HEAD` worktree and diffing the resulting DOM structure.
- **Spec delta** ships at `specs/instruction-card/spec.md`. The delta states five rules that every card keeps. `InstructionSurface` contains the chrome. Fields are data. A card that decodes with a Codama client renders `DecodedInstructionCard`. A card takes one node. One router picks the card of every instruction.
