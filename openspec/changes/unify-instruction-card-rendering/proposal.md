# Proposal: Unify instruction card rendering across the tx page and inspector

## Context

- About 78 `*DetailsCard` components render instructions on two surfaces: `/tx/[signature]` and the inspector. 71 of them draw a card frame.
- Surface chrome leaks into the cards as props. `InstructionCardComponent` swaps the frame in 7 files. `AssociatedTokenDetailsCard` also takes `AddressComponent` and `showProgramField`. `innerCards: JSX.Element[]` is built eagerly in `InstructionsSection` and threaded through four layers to reach `BaseInstructionCard`, so every card in between declares a prop it never reads. The inspector invents `INSPECTOR_RESULT` and `INSPECTOR_SIGNATURE` purely to satisfy card signatures.
- Row markup is copied per field. The 13 System cards were 815 lines, almost all of it `<BaseTable.Row><Cell>label</Cell><Cell className="text-right">…</Cell></BaseTable.Row>` repeated.
- `unify-instruction-parsing` named this work as an explicit out-of-scope follow-up: "collapsing the two per-surface card switches into one render pipeline."
- That change is also what makes the leak observable for System. The inspector reaches System cards only because it landed the System slice and the shared dispatcher — `inspector/InstructionsSection.tsx` calls `dispatcher.fromTransactionInstruction(ix)` and routes its `SYSTEM_PROGRAM_LABEL` case to `SystemDetailsCard`. Before it, the inspector's own `into-parsed-data.ts` fed a separate path. System is therefore a program where one card component must already satisfy two surfaces, while still hardcoding the tx-page frame for both.

## Why

A card should describe what an instruction means. It should not know which page it is on. Today those two responsibilities share one prop bag, so every new surface concern becomes a new prop on every card, and every field becomes eight lines of table markup.

Making chrome ambient (React Context) and fields declarative (data) separates them. Cards shrink to their actual content, and the surfaces stop needing to agree by convention.

### Alternatives considered

- **One `InstructionCard` with a `mode` flag.** Rejected — merges both surfaces' chrome into a conditional. Same coupling, different shape.
- **Keep component injection, just formalise the prop names.** Rejected — the prop count grows with every surface concern, and it is already three (`InstructionCardComponent`, `AddressComponent`, `showProgramField`) for one card.
- **Migrate all 71 cards in this change.** Rejected as unreviewable. 15 are inspector-reachable and carry real chrome deltas that need eyes; the other 56 are mechanical.
- **Start with a tx-page-only program (Stake or Vote, 14 cards each).** Rejected. Zero behaviour risk, but it never exercises the second surface, so the design would land unproven on the only axis that motivates it. System is the one program that is large, inspector-reachable, *and* hardcodes its frame. Its existing test coverage is uneven, and only the inspector side pins the migration: `InspectorPage-SystemProgram.spec.tsx` asserts label-and-value for every row of 9 of the 13 instructions, while `SystemDetailsCard.spec.tsx` covers the tx page with 2 of 13 (Transfer, TransferWithSeed) and asserts only the card title. The tx-page rows are therefore pinned by DOM diffing against a `HEAD` worktree rather than by assertions — see **Impact** below. Closing that gap is a follow-up.
- **Make the field DSL mandatory.** Rejected, and the audit says how often it would bite: ~12 of the 71 frame-drawing cards derive content from a hook, so a pure `fields(info)` cannot produce it. Those cards write their own component and still use `InstructionFields` for the rows they can express. Making the DSL mandatory would have forced hook results through props, pushing the fetching back up into the dispatcher — the coupling this change exists to remove.
- **Build the instruction node tree in this change.** Deferred. It is independent of the surface split and would roughly double the diff.
- **Keep `SignatureContext` and read it in the Anchor event hook.** Rejected. The diff is smaller, but `SignatureContext` defaults to `''`, so an empty string means a missing signature. `InstructionSurface` types a missing signature as `undefined` and requires the key on every surface, and the frame and the cards read the same value. The cost is that every frame render needs a surface. 11 tests in 2 specs and 5 stories rendered a frame without one.
- **Keep a per-surface address renderer.** Rejected. The inspector used `AddressWithContext` with `hideInfo`, which renders the same `<Address link alignRight>` as the tx page. A second renderer adds a field to `InstructionSurface` and changes nothing on screen.
- **Put both surfaces in the entity.** Rejected for the inspector only — `InspectorInstructionCard` imports this entity's barrel, so moving its surface there closes an import cycle. The tx surface has no such edge and lives in the entity, which also lets card tests pick a surface without reaching across layers.

## What Changes

- Add to `app/entities/instruction-card/`:
  - `model/surface.tsx` — `InstructionSurface` (frame, `result`, `signature`) delivered by Context. `useInstructionSurface` throws outside a provider, matching `useInstructionParser`. The frame and the cards read the signature from `InstructionSurface`. A missing signature throws no error. The frame then fetches no raw transaction, and a card shows no program events. `signature` is therefore a required key. The card body draws the `Program` row in the decoded view on both surfaces, so the frame needs neither the width of the body nor the program name. A frame draws its own `Program` row only in the raw view.
  - `model/node.ts` — `InstructionNode`, one object replacing the `ix` + `index` + `childIndex` + `raw` + `innerCards` spread. `InstructionNode` has `programId` as its own field, because a card must not read `node.ix`. A card that reads program events also reads `node.index` and `node.childIndex`.
  - `model/fields.ts` — `address`, `sol`, `bytes`, `string`, `text`, `custom`. `text` takes `string | number`; `custom` is the only markup door and takes a `ReactElement`, not a `ReactNode`, so a labelled blank row is not representable and the descriptors stay data.
  - `ui/InstructionFields.tsx` — renders the label and value rows of migrated cards. The leading `Program` row is the exception: `ProgramField` owns that markup, because the inspector puts its own validator on that row.
  - `ui/ValueCell.tsx` — formats a value by its kind. Field rows and argument rows both render `ValueCell`, to give each kind one format.
  - `ui/DecodedInstructionCard.tsx`, with `model/args.ts` and `model/accounts.ts` — the card of an instruction that a Codama client decodes (Codama IDL, Lighthouse, SAS, PMP). `DecodedInstructionCard` renders the instruction's accounts with role badges. The argument table has a Type column and expandable nested arguments.
  - `ui/InstructionCardView.tsx` — resolves the frame from the surface. The escape hatch for cards that need their own markup, and the carrier for card-derived program events via an `events` prop.
  - `model/define-instruction-card.tsx` — shorthand factory for the common label/value shape.
  - `ui/TxInstructionSurface.tsx` — the transaction page surface.
- The inspector declares `INSPECTOR_SURFACE` in `inspector-surface.ts`, beside its own `InstructionsSection`. Specs import that module, so a spec renders the real inspector surface. This change keeps `INSPECTOR_RESULT`, because unmigrated cards take it as a prop. `INSPECTOR_SURFACE` sets `result` to `INSPECTOR_RESULT`. The last inspector-reachable migration deletes the `result` prop. The Anchor migration deletes `INSPECTOR_SIGNATURE`, because the Anchor card reads the signature from `InstructionSurface`. `INSPECTOR_SURFACE` sets `signature` to `undefined`, because the inspector reads its logs from a simulation, not from a fetched transaction.
- Migrate all 13 System cards to `defineInstructionCard`. No file under `app/components/instruction/system/` imports `Address`, `BaseTable`, or `InstructionCard` any more.
- `SystemDetailsCard` builds the node from the props the two `InstructionsSection`s still pass.
- Migrate `AnchorDetailsCard` to `InstructionCardView`. The card draws the `Program` row from `node.programId`.
- Delete `SignatureContext`. `InstructionCard`, the tx-page frame, reads the signature from `InstructionSurface`, so the frame and the cards read one value. The receipt page provided `SignatureContext` and rendered no instruction card.
- `extractEventsFromLogs` gives each event payload to the invocation that logged it, so the card of a CPI child shows the events of that child. `decodeProgramEvents` decodes the payloads, and `ProgramEventsCard` renders the decoded entries. `AnchorDetailsCard` passes `events` only when `decodeProgramEvents` returns at least one entry.

**Out of scope**, tracked as follow-ups: populating `InstructionNode.children` and deleting the eager `innerCards` build; replacing the two per-surface routing switches with a `programId`-keyed registry; migrating the remaining cards; passing the instruction to a card only through `node` ([HOO-2095](https://linear.app/solana-fndn/issue/HOO-2095/decodedinstructioncard-and-anchordetailscard-can-take-node-and-ix-from)).

## Impact

- **Transaction page: no change for System.** Verified empirically for the two fixtures that exist — the rendered cell text, button set, wrapper elements, and `<code>` counts are identical to `HEAD` for Transfer and TransferWithSeed. Every piece is the same component with the same props, which is the argument that carries the other 11 instructions; they have no tx-page fixture to diff.
- **Inspector: three chrome deltas on System cards**, because they previously used the *tx-page* frame on both surfaces. A collapse chevron now appears (`InspectorInstructionCard` does not pass `collapsible`, and `CollapsibleCard` defaults it to `true`); Raw mode gains the hex and accounts block, because `raw` is now forwarded; the Raw-mode Program row uses `AddressWithContext` with `programValidator`. Row labels, order, count, and the single Program row are unchanged. Address rows render the same `Address` as the tx page. All three deltas match the inspector chrome of Token, Token-2022, and ATA.
- **Those three deltas are only reachable when no IDL resolves for the program.** The inspector checks the dynamic IDL tier *before* its program switch — `inspector/InstructionsSection.tsx` returns `IdlInstructionCard` as soon as `useIdlInstructionDecode` resolves, and reaches its `SYSTEM_PROGRAM_LABEL` case only when it does not — so once an IDL resolves for the System program, the IDL card replaces `SystemDetailsCard` outright. Measured against the dev server with the `CreateAccount` fixture, `SystemDetailsCard` is on screen for roughly 0.75–1.75 s and the IDL card holds the surface from then on. The unit tests never resolve an IDL, which is why they observe the migrated card and pin the deltas. The tx page has the opposite order — `features/transaction/ui/InstructionsSection.tsx` runs its program switch first and falls through to the IDL tier — so `SystemDetailsCard` wins there and is what users actually read. This ordering is pre-existing and identical on `master`; this change does not touch it. It does mean the inspector half of the two-surface argument is theoretical for any program that has a resolvable IDL, and that every program migrated after System is shadowed the same way wherever an IDL resolves for it — which depends on an IDL actually being published for that program, and on the cluster and RPC in use. Tracked as [HOO-1194](https://linear.app/solana-fndn/issue/HOO-1194/inspector-prefers-a-fetched-idl-over-curated-instruction-cards).
- **Anchor has deltas on both pages.** On both pages, this change adds a `Program` row to an Anchor card that fails to decode. In the inspector, the Anchor card has the inspector frame instead of the tx-page frame. The four deltas are a collapse chevron, the validated `Program` row in Raw mode, an `m-6` margin around inner cards, and long titles that wrap instead of ending in an ellipsis. Every Anchor card in the inspector has these deltas, because the inspector renders `AnchorDetailsCard` only through `IdlInstructionCard`.
- **Anchor events change on the tx page.** Each card shows only the events that its own invocation logged. On `master`, the card of a top-level instruction and the card of each of its CPI children all showed every event of the top-level invocation, each decoded with the IDL of its own program. So the top-level card showed the event of a CPI child of another program as `Unknown Event`, and each CPI child showed the events of its siblings. The label of an event on the card of a CPI child carries the child index, for example `#1.1 · event 1`. On `master`, the label carried only the index of the top-level instruction. An event that a CPI child logs shows on no card when the card of that child reads no program events, for example `UnknownDetailsCard` or `CodamaInstructionCard`, or when the page renders no inner cards. On `master`, every Anchor card under the same top-level instruction showed that event if it was a `Program data:` payload. A card whose only payloads are `Program log:` payloads that do not decode draws no `Events` section. On `master`, the frame drew an `Events` header over an empty row.
- **Inspector: six deltas on the inspector's own `UnknownDetailsCard`.** The inspector renders the entity card through its own frame. The card is expanded by default instead of collapsed. The title is `<Program>: Unknown Instruction` instead of `<Program> Instruction`. The index badge has the color of the transaction result instead of `info`. The header has a Raw button, which is disabled, because the card opens in raw mode. Inner cards have an `m-6` margin. A long title wraps instead of ending in an ellipsis. On the tx page, `UnknownDetailsCard` renders as on `master`.
- **Inspector: the error fallback of `IdlInstructionCard` draws the inspector frame.** The fallback renders when `AnchorDetailsCard` or `CodamaInstructionCard` throws. Before #1387, the fallback rendered the tx-page `UnknownDetailsCard` with its default tx-page frame, in the inspector too. The fallback now has a collapse chevron, the validated `Program` row in Raw mode, an `m-6` margin around inner cards, and long titles that wrap instead of ending in an ellipsis.
- **Accepted debt.** `InstructionNode.innerCards` still carries pre-rendered elements and is marked deprecated; cards never read it, only the view passes it to the frame. `InstructionNode.children` exists as the documented target and is unpopulated. Both disappear with the tree follow-up.
- **`InstructionNode.ix` is provisional.** It is typed `ParsedInstruction | TransactionInstruction` because the *frame* — not the card — branches on `'parsed' in ix` to choose `BaseRawParsedDetails` over `BaseRawDetails` for the Raw view. When `unify-instruction-parsing`'s follow-up stops producing `ParsedInstruction`, this field has to split into roughly `programId` + `raw` + an optional RPC-parsed payload. `programId` is already split out, for exactly this reason: a card needs it to feed `InstructionFields`, and taking it from `node.ix` at ~12 future call sites would have put those cards in the blast radius of the reshape. As it stands the revision is confined to `InstructionNode` and `InstructionCardView`; no card is affected, because no card reads `node.ix`.
- **Interaction with `unify-instruction-parsing`: this change shrinks its remaining work.** The System slice's canonical `SystemParsed` is built from the same superstruct types the cards take — `system-parser.ts` imports `TransferInfo`, `CreateAccountInfo`, and the rest from `@components/instruction/system/types`, and those resolve to web3.js `PublicKey` via `PublicKeyFromString`. So `defineInstructionCard<TransferInfo>` already consumes the slice's shape, and the `address(label, pubkey: PublicKey)` descriptor is correct after the compat wrap is deleted. Migrating System off the wrap therefore touches **one** file — `SystemDetailsCard` drops its two `create(...)` passes and switches on `sliceParsed.type` instead — rather than re-editing 815 lines of card JSX. Note this alignment exists because `system-parser.ts` imports a web3.js type, which the parser proposal's own rule forbids for slice internals; that pre-existing tension is what makes the two shapes identical today.
- **The field DSL's reach is narrower than System suggests — there are two card styles, not one.** `defineInstructionCard` calls `title` and `fields` as plain functions, so a card whose content depends on a hook cannot use it. An audit of all 71 frame-drawing cards found ~12 in that position: most call `useCluster` for a `url`, and `TokenDetailsCard` resolves mint decimals through `useMintAccountInfo` + `useSWR` to format an amount. Those cards write their own component — which *can* call hooks — and keep `InstructionFields` for the rows they can express, reaching for `custom()` where a value needs a child component. Both styles take chrome from the surface, so the coupling this change removes is removed for all 71; only the factory's brevity is unavailable to the 12. The headline 815 → 155 ratio comes from System, the most uniform program in the repo, and will not generalise at that rate.
- **Program events are a card-derived view prop, not node data.** Unlike `innerCards`, which `InstructionsSection` builds and passes down, events are read from transaction logs *inside* the card (`useAnchorEvents`). The inspector's shell drops them. They therefore arrive as `InstructionCardView`'s `events` prop rather than on `InstructionNode`, and the factory cannot produce them. `AnchorDetailsCard` is the one card that passes `events`.
- **Audit of the capabilities this design must carry.** Beyond events, the same sweep found: `defaultRaw` used by one card (Serum) and already supported; `headerButtons` and `collapsible` used by **no** card — they are passed shell→`CollapsibleCard` internally, so omitting them from `InstructionShellProps` costs nothing; and **no card renders sibling cards**, every one renders exactly one frame, which is what lets `InstructionCardView` assume a single `Shell`. The fragments in `TokenDetailsCard`, `MetaplexTokenMetadataDetailsCard`, and `SolanaAttestationDetailsCard` are row groups inside one card, not multiple cards.
- **Migration guidance for the remaining cards.** 8 card components render `InstructionCard` as their frame. `SerumDetailsCard`, `TokenSwapDetailsCard`, `WormholeDetailsCard` and `CommonInstructionDetailsCard` render only on the tx page. Their migration changes no output, because the tx surface's frame is `InstructionCard`. `TokenDetailsCard` and `MetaplexTokenMetadataDetailsCard` take the frame as the `InstructionCardComponent` prop. Their migration deletes that prop. `BpfUpgradeableLoaderDetailsCard` and `BatchInstructionCard` render in the inspector with the tx-page frame. Their migration needs the same chrome review as System. The inspector renders `BatchInstructionCard` inside `TokenBatchCard`. Migrate one whole program per PR: a partial program leaves two different frames side by side in the inspector.
- **Line count.** System leaf cards 815 → 155.
- **Verification of the System migration.** `tsc --noEmit` clean; eslint clean including `boundaries/dependencies`; the full spec suite passes (378 files, 4122 tests, after the rebase onto `a2107a74`); `next build` compiles with no measurable bundle change — a fresh `build:info` on this branch is byte-identical to one on `master`. `SystemDetailsCard.spec.tsx` is the one spec this change edits, to wrap the card in `TxInstructionSurface`; the rest pass untouched. Parity was probed by rendering both surfaces against a `HEAD` worktree and diffing the resulting DOM structure.
- **Verification of the Anchor migration.** `tsc --noEmit` and eslint are clean. The spec suite has 518 files, and 5722 tests pass. The Storybook tests of the 13 changed story files pass. `AnchorDetailsCard.spec.tsx` covers the frame, the single `Program` row, the child index and the inner cards on both surfaces. The same spec covers program events on the tx page, the event of a CPI child of another program on the card of that child and not on the top-level card, and a `Program log:` payload that does not decode. `extract-events.spec.ts` covers the payloads of nested CPI invocations. `InstructionCard.spec.tsx` covers the Raw fetch on the tx surface and on `INSPECTOR_SURFACE`. Eleven one-line mutations each fail at least one test: the frame check in `extractEventsFromLogs`, the CPI child counter, the reset of that counter, the `childIndex` that `useAnchorEvents` passes, the `childIndex` in the event label, the empty `events` check, the signature check in the frame, a signature on `INSPECTOR_SURFACE`, the Anchor branch outside the `ErrorBoundary`, the signature in `TxInstructionSurface`, and the index that `useAnchorEvents` passes to `extractEventsFromLogs`. Without `withTxInstructionSurface`, every story in `TokenBatchCard.stories.tsx` throws. A fresh `pnpm build:info` leaves `bench/BUILD.md` byte-identical.
- **Spec delta** ships at `specs/instruction-card/spec.md`. The delta states five rules that a card migration must keep. `InstructionSurface` contains the chrome. Fields are data. A card that decodes with a Codama client renders `DecodedInstructionCard`. A card takes one node. A program migrates whole.
