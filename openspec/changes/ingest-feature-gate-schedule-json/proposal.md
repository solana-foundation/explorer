# Proposal: Ingest the feature-gate schedule from Anza's JSON, not the wiki table

## Context

- **The ingest source was a rendered document.** `scripts/feature-gates/lib/wiki.ts` fetched `Feature-Gate-Tracker-Schedule.md` from the Agave wiki and re-derived structure from it: a regex found GitHub-flavored tables, a second regex found the heading above each table, headings starting with `Pending` selected the tables to import, and cells were split out of `|`-delimited lines. The [rebuild-feature-gate-pipeline](../rebuild-feature-gate-pipeline/proposal.md) change accepted this explicitly ("a column rename will still break parsing — by design").
- **Anza now publishes the same schedule as data.** `feature-gate-tracker-schedule.json`, alongside the markdown page on the same wiki, is a section-name → row-array map: `Fully Activated`, `Pending Mainnet Beta Activation`, `Pending Devnet Activation`, `Pending Testnet Activation`. Rows carry typed fields — `Feature ID`, `Title`, `Description`, `Devnet Epoch`, `Testnet Epoch`, `SIMDs`, `Owners`, and one array per client version floor — instead of pipe-separated cells.
- **The markdown table lost data we wanted.** Its single `Description` column was the feature *title*; the long-form description had to be fetched from the linked SIMD markdown for every row. The `Owner` column was never parsed at all, so `owners` has been written as `[]` since the pipeline was rewritten. The JSON carries `Title` and `Description` as separate fields and `Owners` as an array.
- **The JSON also carries columns we don't read.** `Min FRD Versions` is in the document today and is not in `FeatureGateSchema`; more will follow. The parser needs a stance on unknown fields that differs from its stance on renamed ones.

## Why

The pipeline should consume the machine-readable artifact upstream now publishes, so that ingestion depends on field *names* rather than on document *layout* — and so the two fields the markdown table couldn't give us (`owners`, upstream `description`) land without a second HTTP fetch.

Alternatives considered:

- **Keep scraping the markdown table.** Zero work. Rejected: we'd keep re-deriving structure that upstream already hands us structured, keep writing `owners: []`, and keep two regexes (table shape, preceding heading) as load-bearing infrastructure. Table layout is also the more fragile contract of the two — reordering columns, adding a column, or switching a section from `###` to `##` all change the parse; none of that has an analogue in the JSON.
- **Read the JSON but keep the markdown as a fallback when the JSON 404s.** Tempting for a source that's new. Rejected: two parsers, two fixture sets, and a silent-degradation path where a JSON outage produces rows with no `owners` — and nobody notices, because the run still succeeds. The cron runs daily and opens a PR; a hard failure on one day's run costs one day of freshness and is visible.
- **Validate the whole document, every section.** Simpler to state. Rejected: it couples the nightly run to the shape of `Fully Activated` — 239 rows we never import. The markdown parser deliberately asserted columns only on the tables it read, and that leniency is worth keeping.
- **Reuse `object()` (exact) from `feature-gates-schema.ts` for the upstream rows.** Consistent with the write contract. Rejected: opposite requirements. Our own JSON is a closed contract where a stray key means a writer bug, so exact matching is right there. Anza's document is open and growing (`Min FRD Versions` arrived after the pipeline was written), so an unknown key must not break the cron — while a *renamed* key we read must. `type()` with required fields gives exactly that split.
- **Adopt `Min FRD Versions` in the same change.** The data is right there. Rejected: it's a schema + UI change (a new column in `FeatureGateTable`, a new field in `FeatureGateSchema`, backfill semantics for 95 existing rows), independent of where ingestion reads from. Left as a follow-up so this change stays a source swap.

## What Changes

- **`scripts/feature-gates/lib/wiki.ts` is replaced by `scripts/feature-gates/lib/schedule.ts`.** `fetchWikiFeatures` becomes `fetchScheduledFeatures`, reading `https://raw.githubusercontent.com/wiki/anza-xyz/agave/feature-gate-tracker-schedule.json`. The markdown-shape helpers (`extractTables`, `parseTable`, `precedingHeading`, `wikiRowToFeature`, `splitCsv`, `parseIntOrNull`, the `MarkdownTable` type, both regexes) are gone; `featuresFromSchedule`, `scheduleEntryToFeature`, `parseEpoch`, and `compact` take their place. The rest of the pipeline is untouched — the stage still returns `FeatureGateDraft[]` plus the proposals map.
- **Validation moves from a column-name assertion to a `superstruct` struct.** The document is validated as `record(string(), array(unknown()))`, then each *pending* section's rows against `ScheduleEntrySchema` — a `type()` (loose) struct whose fields are all required. Unknown upstream columns pass; a renamed field the mapper reads fails with the section name in the message. A document with no `Pending …` section fails too, which is the "upstream restructured the whole file" case that the old heading filter would have turned into a silent zero-row import.
- **`owners` is now populated on new rows** from the `Owners` array, and `description` is seeded from upstream `Description` when present (16 of 252 rows today) instead of always starting empty. The SIMD-markdown back-fill still fills the rest, unchanged.
- **`simd_link` stays index-aligned with `simds`.** A row with no SIMD gets `[]` on both, where the markdown parser produced `simds: []` with `simd_link: ['']` (readers pair the arrays positionally and drop unpaired entries, so the placeholder was inert — but it was still a lie on disk).
- **Epoch cells accept `number`, `null`, and `''`.** The JSON mirrors the table's blank cells, so `''` and unparseable text both mean "no epoch yet".
- **Fixtures and tests follow the source.** `agave-wiki.md` / `real-agave-wiki.md` are replaced by `agave-schedule.json` (hand-written, covering the dual-SIMD, blank-epoch, no-SIMD, and unknown-column cases) and `real-agave-schedule.json` (live snapshot, minified); `wiki.spec.ts` becomes `schedule.spec.ts`; `scrape-pipeline.spec.ts` runs against the JSON snapshot; `refresh-test-fixtures.ts` refreshes it.

## Impact

- **Cron behaviour.** One fewer HTTP request per run in the common case is not the point — the network footprint is effectively unchanged (one document fetch, the proposals listing, three RPCs, the SIMD back-fills). New rows now arrive with `owners` filled and sometimes with `description` already set, which slightly reduces the SIMD-summary fetch count.
- **Existing rows are not backfilled.** `appendNewFeatures` still only appends unseen keys, so the 93 rows already on disk keep `owners: []`. Populating them is a one-off migration, not part of this change; the refresh policy in [rebuild-feature-gate-pipeline](../rebuild-feature-gate-pipeline/specs/feature-gate-data/spec.md) ("schedule-sourced metadata is set on first import only") is unchanged and still governs.
- **The failure mode moves, it does not disappear.** A renamed field still breaks the run by design. What no longer breaks it: an added column, a reordered column, a reordered or renumbered section heading level, or a change in table formatting.
- **Accepted risk (new, less-battle-tested upstream artifact).** The JSON is generated by Anza from the same source as the wiki table; if generation breaks upstream we fail loudly on the schema (or on a base58 `key` at the write boundary) rather than importing wrong rows. The daily cadence bounds the cost of a bad day to a skipped run.
- **Docs.** [`rebuild-feature-gate-pipeline/design.md`](../rebuild-feature-gate-pipeline/design.md) records the pipeline as it was designed, including the markdown URL in its external-sources table; it is left as the historical record, and the spec delta beside this proposal carries the superseding requirement.
